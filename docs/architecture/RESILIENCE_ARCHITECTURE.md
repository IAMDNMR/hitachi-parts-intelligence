# Failure / Resilience Architecture

Source of truth for *business* behaviour: Phase 1 `FAILURE_AND_EXCEPTION_CASES.md`. This document adds the *technical* handling pattern for each case, kept as simple as the situation justifies (principle: do not over-engineer).

|---|---|---|---|---|---|---|---|---|

## Principles used to decide "circuit breaker: yes/no" above

A circuit breaker is introduced only where a dependency is called frequently enough, and its failure mode is slow enough (timeouts rather than instant errors), that *not* having one would make failures compound (queued requests all waiting out the same timeout). At today's confirmed scale (no real external providers connected yet — see `INTEGRATION_ARCHITECTURE.md`), this is a designed-for capability, not something over-built for load that does not exist yet.

## What is deliberately not introduced

- No message broker / queue for retrying failed integration calls — the bounded-retry-then-fail pattern above is sufficient at current scale and confirmed dependency count; a queue can be introduced later if a specific integration demonstrates a need for asynchronous, durable retry (e.g., a very slow carrier booking API) without redesigning this document's other rows.
- No distributed caching layer — the PostgreSQL-held Inventory cache (`AVAILABILITY_ARCHITECTURE.md`) is sufficient for the freshness model defined there.
