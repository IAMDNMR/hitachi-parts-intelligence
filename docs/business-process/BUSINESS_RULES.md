# Business Rules

Cross-cutting rules and invariants that apply across multiple stages of `HCME_PARTS_FULFILMENT_PROCESS.md`. Each rule is numbered for traceability from other documents and from future test/validation work.

| ID | Rule | Applies to | Rationale |
|---|---|---|---|
| BR-01 | Missing inventory data must never be interpreted as zero stock. A source that cannot be reached or returns untrustworthy data is recorded as `UNKNOWN`, never as `0`. | Availability | Silently treating "no data" as "no stock" would incorrectly remove real fulfilment options. See `AVAILABILITY_PROCESS.md`. |
| BR-02 | Two simultaneous requests must not be able to successfully allocate the same final unit of inventory. | Allocation | Production correctness requirement, independent of any specific technical mechanism. See `ALLOCATION_PROCESS.md` §3. |
| BR-03 | Cheapest (or fastest) does not automatically win when multiple Fulfilment Options exist. The set is presented; a human/business selects. | Fulfilment Options / Selection | Preserves business judgement (e.g., constraints, urgency, dealer relationship) that a pure cost/time sort would ignore. See `FULFILMENT_PROCESS.md`. |
| BR-04 | Price is resolved at order time from an approved pricing source/rule; it is never treated as a fixed, globally-cached part attribute. | Order | Confirmed industry pattern (Phase 0): OEM parts pricing is dealer/account/login-dependent, not published. See `ORDER_PROCESS.md` §3. |
| BR-05 | An Order is only created after its Allocation reaches `CONFIRMED`. | Order | Prevents ordering against stock that was never actually committed. See `ORDER_PROCESS.md` §1. |
| BR-06 | Any `RESERVED` or `CONFIRMED` allocation tied to a request that is cancelled, fails, or expires must be explicitly released back to available stock. | Allocation | Prevents stock being permanently "lost" to a dead request. See `ALLOCATION_PROCESS.md` §2, §6. |
| BR-07 | No Hitachi-specific allocation priority or VOR/emergency policy is assumed. Only the system capability to support a future policy is defined; the policy itself is a business decision to be made later. | Allocation | Phase 0 research found no such policy publicly confirmed for Hitachi — see `HCME_CONFIRMED_VS_UNKNOWN.md`. |
| BR-08 | Machine telemetry (ConSite, the Telematics API, or any future signal) may never become a required dependency of any stage. It may only ever act as an optional upstream trigger into Select Part. | Select Part / whole process | Explicit Phase 1 scope boundary — see `PHASE_1_DECISIONS.md` §3 and `HCME_PARTS_FULFILMENT_PROCESS.md` §Future Inputs. |
| BR-09 | No automatic parts ordering, automatic allocation, or automatic fault-triggered action may occur without an explicit human/business step in the chain (Select Part, Fulfilment Selection). | Whole process | Same rationale as BR-08 — keeps the human decision points from Phase 0's design intent intact. |
| BR-10 | The Dealer is modelled as a first-class business entity (identity, branch, territory, capabilities), never as a free-text field on an order or shipment. | Dealer, Order, Shipment, Service | See `ACTORS_AND_RESPONSIBILITIES.md` §3. |
| BR-11 | The Fulfilment Request reaches `COMPLETED` if and only if its Shipment is `DELIVERED` and its Service Job is `COMPLETED`. No other condition closes the request. | Close | Deterministic, internally-verifiable closing condition. See `DEALER_SERVICE_PROCESS.md` §3. |
| BR-12 | A received shipment is checked against its Order (part, quantity) before a Service Job is opened; a mismatch is a failure case, not a silent pass-through. | Dealer receiving | Prevents installing/servicing against an incorrect part or quantity. See `FAILURE_AND_EXCEPTION_CASES.md`. |
| BR-13 | Every UNKNOWN item recorded in `HCME_CONFIRMED_VS_UNKNOWN.md` stays UNKNOWN in every other document; no document may silently resolve it into an assumed fact. | All documents | Explicit instruction for this phase; enforced by cross-referencing rather than restating. |
| BR-14 | Every Fulfilment Option, Allocation, Order, Shipment and Service Job carries enough reference data (timestamps, source system where known, actor) to reconstruct the full trace at Close. | Whole process | Supports the "production-readiness from the beginning" requirement without deciding the technical audit mechanism (Phase 2). |
