# Failure & Exception Cases

Every failure path in the process, in one place. For each case: what the user sees, what state the request enters, whether retry is possible, whether manual intervention is required, whether the process can continue, and whether an allocation must be released.

No HCME-specific policy is invented for any of these — where the *business* response (e.g., "offer a substitute part") is a policy decision rather than a process-flow fact, it is marked TO-BE and routed to `HCME_BUSINESS_QUESTIONS.md`.

| # | Case | What the user sees | Request state | Retry possible? | Manual intervention? | Process can continue? | Allocation released? |
|---|---|---|---|---|---|---|---|
| 1 | Part does not exist | Clear "part not found" message at Select Part | Never leaves pre-`REQUESTED` | Yes — correct the part number | No | No (blocked at entry) | N/A — no allocation yet |
| 2 | Part is not orderable (discontinued/blocked) | "This part is not currently orderable" | Never leaves pre-`REQUESTED` | No, unless the block is lifted upstream | Yes — business/catalogue decision (TO-BE: substitute part offering) | No | N/A |
| 3 | Fitment is uncertain | Warning that compatibility could not be confirmed for the given machine/context | `REQUESTED`, flagged | Yes — user may proceed with an explicit acknowledgement, or supply more machine/context detail | Optional — TO-BE whether uncertain fitment blocks or only warns | Yes, if the business allows proceeding on acknowledged uncertainty (TO-BE) | N/A — before allocation |
| 4 | Inventory is unavailable (a source reports zero/insufficient) | That source shown as unavailable; other sources still shown | `AVAILABILITY_CHECKED` | Yes — other sources/options remain | No | Yes, via another source | N/A |
| 5 | Inventory data is stale | Source shown with an `UNKNOWN` status and its last-known timestamp, not a false "confirmed" figure | `AVAILABILITY_CHECKED` | Yes — refresh the query | No | Yes, via other sources or a lower-confidence option (see BR-01) | N/A |
| 6 | Inventory source is unavailable (system down/unreachable) | That source shown as `UNKNOWN`, not `0` | `AVAILABILITY_CHECKED` | Yes — automatic or manual re-query | No, unless prolonged (TO-BE escalation policy) | Yes, via other sources | N/A |
| 7 | Requested quantity exceeds availability | The honest available quantity is shown; user may reduce quantity, choose a partial/split option, or select a different source | `AVAILABILITY_CHECKED` | Yes | No | Yes | N/A — before allocation |
| 8 | Partial availability exists across sources | Options reflect a possible split fulfilment (see `FULFILMENT_PROCESS.md`) | `AVAILABILITY_CHECKED` | Yes | No, unless the business disallows split fulfilment (TO-BE) | Yes | N/A |
| 9 | Fulfilment option cannot be calculated (no transport data) | That option marked incomplete/estimated rather than hidden or fabricated | `AVAILABILITY_CHECKED` | Yes — other options may still be viable | No | Yes, if any other option is viable; otherwise blocked until data available | N/A |
| 10 | Transport provider is unavailable | Options relying on that provider marked unavailable | `AVAILABILITY_CHECKED` | Yes — other providers/options | No | Yes, via other providers | N/A |
| 11 | Allocation fails (insufficient stock at commit time) | "Unable to reserve this option — please choose another" | Fulfilment Request returns toward `OPTION_SELECTED`/`AVAILABILITY_CHECKED`; Allocation → `FAILED` | Yes — select a different option | No | Yes, if another option exists; otherwise → `FAILED` | N/A (nothing was confirmed to release) |
| 12 | Allocation expires (not confirmed within the time window) | "Your reservation has expired — please try again" | Allocation → `EXPIRED`; Fulfilment Request returns to Fulfilment Selection | Yes | No | Yes | Yes — stock returns to available |
| 13 | Order creation fails (pricing unavailable or source rejects) | "We could not complete your order — please try again shortly" | Fulfilment Request remains `ALLOCATED` (not `ORDERED`) | Yes, within a bounded window (TO-BE) | Yes, if retries exhausted | No, until resolved | Yes, if the bounded window is exceeded without resolution |
| 14 | Shipment creation fails | "Your order is confirmed; shipment is being arranged" (no false shipped status shown) | Order remains `ACCEPTED`; Fulfilment Request remains `ORDERED`/`FULFILMENT` | Yes | Yes, if retries exhausted | No, until resolved | No — allocation/order remain valid |
| 15 | Shipment is delayed | Updated ETA and a delay flag, sourced from carrier events only | Shipment → `EXCEPTION`, may return to `IN_TRANSIT` | N/A — informational | Yes, if delay is prolonged (TO-BE escalation) | Yes | No |
| 16 | Shipment is lost | Shipment flagged; customer/dealer informed | Shipment → `EXCEPTION` → `CANCELLED` if confirmed | No, for this shipment | Yes — business decision on replacement (TO-BE) | Only via a new Fulfilment Request if a replacement is pursued | Not applicable to the original allocation (already `CONSUMED`); a replacement request runs its own allocation |
| 17 | Dealer rejects/does not receive shipment | Discrepancy recorded; customer/dealer notified | Shipment stays `DELIVERED`/`EXCEPTION` per carrier; Service Job does not open on a rejected receipt | Yes — re-delivery or investigation (TO-BE process) | Yes | No, until receipt is resolved | Not applicable (allocation already consumed at Order); a correction is a business decision (TO-BE) |
| 18 | Part is damaged | Damage recorded at receipt (condition notes) | Service Job does not proceed past receipt if damage blocks use | Not for the same physical part | Yes — replacement decision (TO-BE) | Only via a new Fulfilment Request for a replacement part | Not applicable to the original (already consumed) |
| 19 | Part cannot be installed | Recorded on the Service Job with notes | Service Job does not reach `PART_INSTALLED`/`COMPLETED` | Depends on cause (TO-BE) | Yes | No, until resolved | Not applicable at this stage |
| 20 | Service job is cancelled | Job marked cancelled with reason | Service Job → `CANCELLED` | No, for this job | Yes | Fulfilment Request does not reach `COMPLETED`; overall outcome is a business decision (TO-BE) | N/A — allocation already consumed |
| 21 | Customer cancels | Confirmation of cancellation shown | Fulfilment Request → `CANCELLED` from whichever state it was in | No | No, if cancelled before shipment; Yes (coordination) if after | No — terminal | Yes, if allocation was `RESERVED`/`CONFIRMED` at time of cancellation (BR-06) |
| 22 | External API is unavailable (any integration point) | The specific stage shows the affected data as `UNKNOWN`/unavailable rather than failing the whole request where avoidable | Depends on which stage; never silently treated as success | Yes — retry per stage's own policy | Yes, if prolonged | Yes, wherever the unavailable system is not strictly required for that step | Only if the outage caused an allocation to expire (case 12) |

## Principles applied consistently above

1. **No silent success and no silent failure.** Every exception is visible to the user in appropriate terms, and every state transition reflects reality.
2. **UNKNOWN is not 0, and UNKNOWN is not "failed."** A source or system that cannot currently answer is represented as unresolved, not as a negative result (BR-01).
3. **Allocation is only released when it is genuinely no longer needed** (cancellation, expiry, unrecoverable failure) — never released speculatively while a request might still succeed (BR-06).
4. **Where the correct business response is a policy question** (substitute parts, replacement handling, escalation thresholds, split-fulfilment defaults), this document flags it TO-BE rather than inventing an HCME policy — see `HCME_BUSINESS_QUESTIONS.md`.
